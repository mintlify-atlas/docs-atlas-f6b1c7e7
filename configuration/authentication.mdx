description: "Cómo registrarse, iniciar sesión y autenticar solicitudes en ViniHotel usando tokens JWT Bearer. Cubre almacenamiento de tokens, expiración, codificación de roles y buenas prácticas de seguridad."
---

ViniHotel usa JSON Web Tokens (JWT) para la autenticación. Tras un inicio de sesión o registro exitoso, el backend devuelve un token firmado que el cliente incluye como encabezado `Bearer` en cada solicitud autenticada posterior. Los tokens son válidos por 7 días de forma predeterminada y son almacenados en `localStorage` por el `apiClient` del frontend.

## Flujo de autenticación

<Steps>
  <Step title="Registra una nueva cuenta">
    Envía una solicitud `POST` a `/api/auth/register` con tu nombre, correo electrónico y contraseña. Se devuelve un token de inmediato — no se necesita un paso de inicio de sesión separado después del registro.

    ```bash
    curl -X POST http://localhost:5000/api/auth/register \
      -H "Content-Type: application/json" \
      -d '{
        "nombre": "Jane",
        "apellido": "Doe",
        "email": "jane@example.com",
        "contrasena": "mysecretpassword"
      }'
    ```
  </Step>
  <Step title="Inicia sesión para recibir un token">
    Envía una solicitud `POST` a `/api/auth/login` con tu correo electrónico y contraseña. El campo de contraseña se llama `contrasena` en la API (el `apiClient` del frontend mapea `password` → `contrasena` automáticamente).

    ```bash
    curl -X POST http://localhost:5000/api/auth/login \
      -H "Content-Type: application/json" \
      -d '{"email":"user@example.com","contrasena":"password123"}'
    ```

    Una respuesta exitosa incluye un campo `token`:

    ```json
    {
      "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
      "user": {
        "idUsuario": 1,
        "nombre": "Juan",
        "apellido": "García",
        "email": "juan@example.com",
        "rol": "client"
      }
    }
    ```
  </Step>
  <Step title="Almacena el token">
    El frontend almacena el token en `localStorage` bajo la clave `token`. El `apiClient` lee este valor al inicializarse para que las solicitudes autenticadas funcionen entre recargas de página:

    ```ts
    this.token = localStorage.getItem('token');
    ```
  </Step>
  <Step title="Incluye el token en las solicitudes">
    Todos los endpoints protegidos requieren un encabezado `Authorization` con el esquema `Bearer`:

    ```bash
    curl -H "Authorization: Bearer YOUR_TOKEN" \
      http://localhost:5000/api/auth/me
    ```

    El `apiClient` agrega este encabezado automáticamente a cada solicitud cuando hay un token almacenado:

    ```ts
    headers['Authorization'] = `Bearer ${this.token}`;
    ```
  </Step>
  <Step title="Cierra sesión">
    Cerrar sesión borra el token tanto de la memoria como de `localStorage`. No se necesita ninguna llamada al servidor — el token simplemente deja de enviarse.

    ```ts
    apiClient.clearToken();
    localStorage.removeItem('token');
    ```
  </Step>
</Steps>

## Expiración del token

Los tokens expiran tras `JWT_EXPIRE` (predeterminado `7d`). Cuando se envía un token expirado o inválido, el backend responde con:

```json
{ "error": "Invalid token" }
```

con el estado HTTP `401`. El `apiClient` del frontend intercepta las respuestas `401` y redirige al usuario a `/login`:

```ts
if (response.status === 401) {
  this.clearToken();
  window.location.href = '/login';
}
```

## Roles de usuario

El rol del usuario se codifica en el payload del JWT junto con `userId`:

```js
jwt.sign({ userId, role }, JWT_SECRET, { expiresIn: process.env.JWT_EXPIRE || '7d' })
```

Existen tres roles:

| Rol | Acceso |
| --- | --- |
| `client` | Rol predeterminado. Puede crear y gestionar sus propias reservas y facturas. |
| `staff` | Puede acceder a las rutas de nivel de personal además de las rutas de cliente. |
| `admin` | Acceso completo, incluyendo gestión de hoteles, habitaciones y usuarios. |

El rol se verifica por ruta mediante `staffMiddleware` y `adminMiddleware` en `src/middleware/auth.js`. Intentar acceder a una ruta restringida con privilegios insuficientes devuelve HTTP `403`.

## Credenciales de prueba

El servidor siembra estas cuentas automáticamente en el primer inicio si aún no existen:

<CodeGroup>

```text Cuenta de cliente
Email:    juan@example.com
Password: password123
Role:     client
```

```text Cuenta de administrador
Email:    admin@example.com
Password: admin123
Role:     admin
```

</CodeGroup>

<Note>
  También se siembra una segunda cuenta de cliente (`maria@example.com` / `password123`) para pruebas de escenarios multi-usuario.
</Note>

## Buenas prácticas de seguridad

<Warning>
  El valor predeterminado de `JWT_SECRET` (`your_super_secret_jwt_key_change_this`) es público. Cualquiera que conozca este valor puede falsificar tokens válidos para cualquier usuario de tu sistema. Siempre reemplázalo antes de desplegar.
</Warning>

- **Cambia `JWT_SECRET`** por una cadena hexadecimal aleatoria de 64 bytes antes de pasar a producción. Consulta la página de [Variables de Entorno](/configuration/environment-variables) para el comando de generación.
- **Usa HTTPS** en producción. Los tokens JWT enviados por HTTP simple pueden ser interceptados y reproducidos.
- **Nunca almacenes contraseñas en el frontend.** Las contraseñas se hashean con bcrypt en el backend antes del almacenamiento — el texto plano nunca persiste.
- **Nunca expongas tokens en URLs.** Siempre pasa los tokens en el encabezado `Authorization`, no como parámetros de consulta.
